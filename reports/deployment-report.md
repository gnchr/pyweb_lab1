# Отчёт: автоматизированное развёртывание статического сайта

## Объект и границы проверки

Проект `pyweb_lab1`, MkDocs 1.6.1, Material 9.7.7, Python 3.12. Содержимое сайта
намеренно оставлено заглушкой. Дополнения посвящены доставке и эксплуатации;
файлы отчёта не включены в опубликованный сайт.

На 03.10.2026 проверены локальная строгая сборка, регрессионные тесты,
поиск в браузере без внешних ресурсов и демонстрация управления версиями
с настоящим локальным HTTP-сервером. **Реальная выкладка на Helios в этой
итерации не выполнялась**: доступ и секреты не предоставлены. Реальные
времена GitHub Pages/Helios и надёжность серверов не измерены. Ниже разделены
проверенные свойства реализации и ожидаемые эксплуатационные особенности.

## Реализация

`pages.yml` использует официальный artifact-подход: строгая сборка →
`upload-pages-artifact` → `deploy-pages` → публичный healthcheck.
Деплой получает разрешения `pages: write`, `id-token: write`, зависимость
от build и environment `github-pages`, согласно
[документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
Альтернативный подход с `peaceiris/actions-gh-pages` записывает готовый HTML
в ветку `gh-pages` и требует выбора этой ветки источником Pages. Он проще
для просмотра истории готовых файлов, но добавляет build-артефакты в Git.
Здесь выбран artifact-подход; одновременно включать оба подхода не следует.

`helios.yml` вызывается после успешного CI в том же workflow: при открытии/обновлении PR
публикует preview, после merge в main — основную версию. Также доступны
ручные `rollback` и `recover`; обычный deploy только автоматический.
Передача идёт по SSH/rsync с отдельным
ключом CI, строгой проверкой host key и без интерактивной аутентификации.
Закрытый ключ не хранится в Git; подготовка описана в README. Для сервера
необходимы rsync, POSIX shell, стандартные Unix-утилиты и общая файловая система
между `public_html` и приватным хранилищем. **Python на Helios не нужен**:
он используется только на GitHub runner для сборки, SSH-оркестрации и healthcheck.
Управление релизами на сервере выполняют `helios_release.sh` и `helios_remote.sh`,
передаваемые на stdin `sh -s` без установки файлов или дополнительного ПО.

Структура:

```text
~/public_html/pyweb_lab1/          # основная ветка, действующая статика
    previews/<slug>-<hash>/       # отдельный сайт каждой другой ветки
~/.pyweb_lab1-deploy/             # права 700, вне HTTP document root
    staging/<release>/           # незавершённые / подготовленные версии
    backups/<channel>/<operation>/
    history/<channel>.previous    # идентификатор backup предыдущей версии
    transaction/                 # незавершённый журнал переключения
    committed-<operation>/       # подтверждённый журнал (точка commit)
    lock                         # атомарный hard link, PID и operation
```

Корень означает **корень проекта** `~/public_html/pyweb_lab1`, не общий
`public_html`: остальные лабораторные работы не затрагиваются. Основная ветка
берётся из default branch репозитория; для неё внутренний channel равен `main`.
Для preview имя нормализуется и дополняется 12 знаками SHA-256 исходного имени,
поэтому `feature/a`, `feature-a`, `Feature/A` получают разные каталоги.
Деплои main сохраняют preview, откат main не возвращает preview к старым версиям.
История каждого preview независима. Удаление ветки не удаляет опубликованный
preview автоматически. Для ручного отката preview требуется существующая ветка.

В сборку передаётся правильный `SITE_URL`, включая подкаталог preview.
CSS/JS и поиск используют относительные пути. На сервер отправляется содержимое
`site/`, без дополнительной вложенности `site`. Настройки находятся в GitHub
Variables/Secrets, а не в исходниках.

Доставка сначала создаёт уникальный staging, затем вызывает rsync без
`--delete`, и лишь при exit code 0 активирует полученный каталог.
Режим `--archive --compress --chmod=D755,F644` сохраняет структуру и задаёт
права. Семантика rsync описана в его
[официальном руководстве](https://download.samba.org/pub/rsync/rsync.1).
И staging, и backups находятся вне публичного дерева. Перед переключением
проверяются пути, символьные ссылки, метаданные и маркеры. Старый каталог
переименовывается в backup, новый — в публичный каталог.

Операции сериализованы общей группой GitHub concurrency с `queue: max`,
`cancel-in-progress: false` и серверной файловой блокировкой. Это позволяет
сохранить ожидающие выкладки разных веток вместо замены единственного pending
job. Очередь ограничена 100 ожидающими запусками; порядок определяется моментом
постановки, а не гарантированным порядком push, согласно
[документации concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
При переполнении возможна отмена новых запусков — соответствующий preview/
production workflow нужно повторить через Re-run jobs.

## Healthcheck и откат

Каждый релиз получает `deployment.json` и скрытый HTML-комментарий
`PYWEB_LAB1_RELEASE:<id>`. Проверка требует HTTP 200, общую контрольную строку
`PYWEB_LAB1_DEPLOYMENT_OK` и **маркер именно ожидаемого релиза**. Ответ 200 со
старым HTML не считается успехом. Дополнительно проверяются CSS/JS, worker и
непустой поисковый индекс. Есть ограниченные повторы с задержкой для временных
ошибок/кэша; при исчерпании попыток скрипт возвращает 1, job завершается ошибкой.

При неуспешном healthcheck Helios автоматически пробует восстановить previous,
если он существует, и повторно проверить восстановленный сайт. Исходная ошибка
не скрывается: job остаётся failed даже после удачного восстановления.
Проверка `--expect-release` запрещает автоматическому откату заменить другой
релиз, появившийся после проверяемого. При первой публикации previous отсутствует:
ошибка остаётся видимой, исправление требует нового деплоя.

Ручной возврат: Actions → Helios rollback and recovery → Run workflow → action `rollback`,
target_branch `main` или нужная ветка. Для команды `recover` используется
тот же интерфейс. Откат не требует пересборки или старого Git commit: на сервере
сохранена готовая предыдущая статика. Повторный rollback переключает версии
обратно. Автоматической очистки нет: нужно контролировать квоту, не удаляя
актуальный previous, журнал и используемые staging.

## Локальная демонстрация

Выполнено:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m mkdocs build --strict
.\.venv\Scripts\python.exe scripts\smoke_test.py --directory site
.\.venv\Scripts\python.exe scripts\browser_test.py --directory site --channel msedge
.\.venv\Scripts\python.exe scripts\demo_deployment.py --report reports\rollback-demo.json
```

Протокол: [rollback-demo.json](rollback-demo.json). Используется тот же
shell-код `helios_release.sh`, что запускается на Helios через SSH; `ReleaseStore`
теперь только локальный Python-адаптер для запуска этого shell-кода. Файлы
и HTTP находятся локально. **Это демонстрация алгоритма, не доказательство работающего SSH-деплоя.**

| Проверка | Наблюдаемый результат |
| --- | --- |
| Публикация v1, затем v2 | HTTP 200 и уникальный маркер соответствующей версии |
| Откат v2 → v1 | HTTP 200, маркер v1; preview сохранён |
| Удалён JS bundle тестового v3 | Healthcheck получает HTTP 404 ресурса, откат восстанавливает v1 |
| В staging передан только index.html | Публичная v1 остаётся доступна с HTTP 200 |
| Прерывание сразу после перемещения старой версии | HTTP 404 до восстановления; после recover — HTTP 200, v1 |
| Прерывание после установки новой версии до завершения журнала | Новая версия доступна, но recover возвращает подтверждённую v1 |

Прерывание переключения моделируется `kill -9 $$` внутри реального тестового
shell-процесса, оставляя журнал и устаревшую блокировку. Следующий shell-процесс
восстанавливает версию и освобождает блокировку. Обычная ошибка моделируется
`exit 97`, при котором EXIT trap выполняет восстановление сразу. Точки инъекции
подменяются только в памяти локального тестового адаптера, не включаются в
продукционную SSH-команду. Это не эксперимент с отключением питания сервера.
Регрессионные тесты проверяют обе фазы и обычные ошибки.
Все 35 тестов успешно пройдены на локальной машине с Git for Windows.
Отдельный тест проверяет, что SSH запускает `sh -s`, не Python, и передаёт
только shell-исходники; блокировка работающего процесса запрещает чужое восстановление.
Проверяются также
независимость preview, отсутствие активации после ошибки rsync, коллизии имён,
невалидные пути, HTTP не-200 и правильный HTTP 200 с неверным маркером.
Функциональный браузерный тест выполняет поиск в трёх подкаталогах и блокирует
внешние сетевые ресурсы.

## Что происходит при обрыве

| Момент обрыва | Действующая версия / восстановление |
| --- | --- |
| Сборка или проверка до SSH | Публичный сайт не меняется |
| Середина rsync | Старая версия не меняется; неполный staging остаётся приватным; новый запуск создаёт новый release |
| Обычная ошибка переключения | Обработчик использует журнал и возвращает старый каталог |
| Процесс остановлен между двумя rename | Публичный каталог отсутствует: возможен 404; `recover` или следующая операция возвращает старый каталог |
| Новая версия установлена, журнал ещё существует | Следующая операция восстанавливает старую подтверждённую версию |
| Журнал переименован в committed, но SSH-соединение оборвалось до получения ответа | Версия могла уже смениться; pipeline failed, результат неопределён для runner. Нужно `recover` и публичный healthcheck, а при необходимости `rollback` |
| Публичный healthcheck не прошёл | Попытка автоматического rollback; job всё равно failed; если SSH/HTTP недоступны, проверка восстановления тоже неуспешна |

Два переименования **не являются одной атомарной операцией**. Окно 404 обычно
короткое, но может длиться до следующей команды при принудительной остановке.
Журнал восстанавливает незавершённую операцию, а не обеспечивает нулевой простой.
Защита рассчитана на ошибки команд/процесса, не на повреждение диска, удаление
backups вручную или доказанную устойчивость к внезапному отключению питания.
`recover` без незавершённого журнала не меняет уже подтверждённый релиз.
Блокировка создаётся атомарным hard link к заполненной записи PID/operation.
PID погибшего процесса проверяется `kill -0`, после чего устаревшая блокировка
снимается под отдельной блокировкой восстановления. Повторно использованный PID,
повреждённая запись или остановка процесса в момент захвата `lock-recovery`
требуют ручной проверки; такие состояния приводят к отказу, а не опасному
параллельному переключению. При отмене после commit новый релиз сохраняется.

GitHub Pages не использует наш rsync и не перезаписывает файлы по одному.
Сбой загрузки artifact до шага deploy не публикует неполный artifact.
Состояние после обрыва самого deploy нужно установить по статусу deployment
и уникальному маркеру публичного URL; не следует считать failed job доказательством,
что сайт остался старым. Наша схема не предоставляет автоматический rollback Pages:
возврат там выполняется повторным деплоем выбранного старого commit.

## Сравнение площадок

Это сравнение архитектуры, не измеренная оценка SLA.

| Критерий | GitHub Pages | Helios в данной реализации |
| --- | --- | --- |
| Время доставки | Передача artifact, ожидание отдельного deploy job, работа Pages и появления версии по HTTP | SSH-проверки, передача полного релиза rsync, копирование preview при main, переключение, HTTP |
| Надёжность | Меньше собственной серверной логики; состояние публикации отслеживается Pages | Сохранён previous, журнал и блокировка; зависимость от SSH, shell/Unix-утилит, дисковой квоты и HTTP Helios; возможен 404 при переключении |
| Отладка | Actions logs, deployment status, artifact, HTTP; нет доступа к файловой системе хостинга | Те же логи плюс SSH, staging, backup, history и журнал; больше возможностей и ответственности |
| Preview | В этой конфигурации только main, отдельные branch-preview не настроены | Каждая ветка имеет отдельный публичный URL и историю |
| Возврат версии | Повторная публикация старого commit | Ручной/автоматический rollback сохранённой статики без сборки |

Прямой rsync потенциально уменьшает задержку доставки, но здесь каждый staging
пустой, поэтому передаётся весь сайт, а не только diff с публичной версией.
Большое число preview удорожает копирование main. Утверждать, какая площадка
быстрее или надёжнее в данном окружении, до реальных запусков нельзя.

### Методика и оставшиеся замеры

В обоих workflow начало измерения ставится перед передачей готовой статики,
окончание — после публичного healthcheck. Pages включает upload artifact и
переход между build/deploy jobs; Helios — SSH/rsync и активацию. Начальная сборка,
установка зависимостей и ожидание старта workflow не входят в `delivery_seconds`.
При failed healthcheck Helios итог включает попытку отката; такие значения
сравниваются отдельно от успешных. Время healthcheck и upload/activate Helios
также сохранены отдельно. Часы Pages находятся на разных runner, поэтому
малые различия измерений не стоит трактовать как точный benchmark.

JSON виден в Actions Summary и artifacts `pages-measurements-*`,
`helios-measurements-*`. Для сравнения нужно выполнить минимум три успешные
выкладки одного commit/размера сайта на обе площадки и записать медиану,
диапазон, ссылки на run, размер artifact и дату. Отдельно выполнить
rollback Helios после двух успешных релизов, проверить маркеры и записать
run URL. Исходная цель с живой демонстрацией на Helios требует этих действий
после заполнения секретов.

| Площадка | Run URLs | Успешные значения delivery_seconds | Медиана |
| --- | --- | --- | --- |
| GitHub Pages | Не измерено | Не измерено | Не измерено |
| Helios | Не измерено | Не измерено | Не измерено |

Числа из локального JSON относятся только к демонстрации и не подставляются
в эту таблицу. Для фактической оценки надёжности следует также фиксировать
число попыток, долю успешных healthcheck и причины ошибок; одного удачного
деплоя недостаточно для вывода о доступности сервиса.

## Отладка и ограничения

### Доработка CI и защиты merge

На 08.10.2026 ни один workflow не подписан на push. `preview.yml` на
opened/reopened/synchronize PR запускает полный `CI / build` для head SHA,
затем через `needs: ci` вызывает Helios preview. `merge.yml` на closed с
merged=true проверяет метаданные merge и отправляет `repository_dispatch:
main-merged`. `production.yml` получает main-контекст, запускает полный CI
merge-коммита, затем параллельно вызывает Helios main и GitHub Pages.
Закрытие без merge и прямой push в main ничего не публикуют. Обновление
открытого PR запускает проверки по событию PR, а не по push. Событие merge определяется согласно
[документации GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-pull_request-workflow-when-a-pull-request-merges).

Старые `ci.yml`, `ci-gate.yml`, `wait_for_ci.cjs` и их тест ожидания удалены.
Ожидания внешнего CI нет: dependencies обеспечивают порядок внутри workflow.
Перед checkout production CI проверяет ref=refs/heads/main, факт merge в main,
merge_commit_sha и актуальность main. Не прошедший/отменённый CI не разрешает
деплой. `repository_dispatch` использует default branch и может автоматически
запускаться через GITHUB_TOKEN, согласно
[событиям GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch).
Для ручной операции сначала определяется неизменяемый SHA и запускается тот же
полный CI для rollback/recover. Ручной deploy Helios и Pages удалён.
В checkout деплоя передаётся
проверенный SHA, а не подвижное имя ветки; перед публикацией повторно проверяется,
что ветка не продвинулась.
Ручной Helios выделен в `helios-manual.yml`: только этот workflow определяет SHA
ветки и запускает полный CI перед восстановлением. Reusable `helios.yml`
содержит только job `deploy`, поэтому в preview и основной автоматической
публикации нет пропущенных `Resolve manual target` и вложенного `CI / build`.
Серверная очередь остаётся только в reusable workflow, без двойного захвата
одной concurrency-группы вызывающим и вызываемым workflow.

В `gnchr/pyweb_lab1` для main через GitHub API включены required checks
`CI / build`, `Preview ready`, strict up-to-date и enforce admins.
Источник проверок закреплён за GitHub Actions (app 15368). Конфигурация
хранится в `.github/branch-protection.json`, но ограничения задаются GitHub,
не YAML-деплоем. Поэтому непройденные проверки действительно блокируют merge,
а не только окрашивают pipeline в красный. Отключённый автоматический Helios
завершает обязательную проверку ошибкой, а не допустимым skipped-статусом.
Итоговый PR-job `Preview ready` с `if: always()` требует успешного
CI и деплоя, поэтому skipped/cancelled/timeout также блокируют merge.
Это необходимо, поскольку GitHub может принять skipped required job, как
описано в [документации required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks).

После успешной публикации и healthcheck URL размещается в обновляемом PR-
комментарии, Actions Summary и environment. Старый `preview-link.yml` удалён:
при открытии PR теперь выполняются полный CI и выкладка,
а не только поиск ранее опубликованной ссылки. Отфильтрованы чужие forks,
закрытые PR и устаревшие SHA.
Новые workflows в этой доработке проверяются локально; реальное выполнение
новой схемы на GitHub требует commit/push изменений.
Локально новая схема проверена 51 Python-тестом и 15 Node-тестами: все прошли,
включая отсутствие push-триггеров, порядок CI → deploy, dispatch только после
merge, main-контекст и проверку merge SHA до checkout.
Также успешно выполнены строгая сборка, smoke-тест и браузерные проверки

### Отказ environment GitHub Pages после merge PR #7

Read-only диагностика GitHub API подтвердила: environment `github-pages`
использует custom branch policy и разрешает только branch `main`. Последний
[production run](https://github.com/gnchr/pyweb_lab1/actions/runs/37828237217)
с event=pull_request завершился failure для `Deploy to GitHub Pages / deploy`,
хотя Pages build и Helios deploy прошли. Полученный пользователем отказ
указывает на `refs/pull/7/merge`, не разрешённый environment. В предыдущем
зелёном run Pages deploy был skipped, то есть успех workflow не доказывал
публикацию Pages.

Причина: checkout merge SHA меняет файлы на runner, но не `github.ref`,
используемый deployment protection/OIDC. Поэтому метаданные merge отдельно
передаются production через repository_dispatch с main-контекстом. Правило
«только main» не ослабляется; PR-refs не добавляются в разрешённые. Перед
Pages build дополнительно проверяется main-ref. При failed CI публикация
штатно пропускается, но весь workflow остаётся failed; при успешном CI deploy
действительно запускается, его ошибка не маскируется веточным условием.
Политики ref описаны в
[документации environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
Фактический успешный запуск исправленной Pages-публикации требует commit/push
и нового merge: старый Re-run использует прежнюю версию workflow и тот же PR-ref.

В ходе доработки исправлены прямое копирование поверх действующего сайта
и первоначальная ошибочная зависимость от Python на Helios: серверная логика
переведена на POSIX shell, Python оставлен только на runner. Также устранены
отсутствие previous, отсутствие preview и возможность принять старый HTML
за удачный новый деплой. Найдены и явно проверены окно 404 между rename,
сохранение preview при откате main и отсутствие активации при ошибке rsync.
Проверки ресурсов ловят ситуацию «index.html доступен, но JS отсутствует».

Публичные preview доступны любому посетителю. В environment `helios` необходимо
разрешить доверенные preview-ветки. Workflow не запускается на PR из чужих forks.
Отдельный SSH-ключ не делает небезопасный код доверенным: права на изменение
веток/workflows должны оставаться у доверенных участников.
